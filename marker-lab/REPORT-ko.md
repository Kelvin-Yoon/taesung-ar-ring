# 태성고 AR 링: 10mm 마커 분석과 시험 안내

작성: 2026-10-19 (한국 시간). **10mm 인식을 보장하지 않습니다.** 이 패키지는 새 도안·정합된 패턴 파일·실측 인쇄물·기존 AR 장면을 이용한 비교 시험 도구입니다. 실제 휴대폰과 인쇄된 반지의 성능 시험은 아직 수행하지 않았습니다.

## 1. 사진에서 확인한 사실과 추정의 구분

원 대화의 `KakaoTalk_20261019_104944526.jpg` 원본을 열어 확인했습니다. 밝은 바탕의 태성 로고 스티커가 회색 3D 프린팅 반지 상판 안쪽에 붙어 있습니다. 파란 작은 네모 표식과 검정·파랑 로고가 보이지만 **로고 주변에 연속된 검은 정사각형 테두리는 보이지 않습니다.** 상판과 스티커 모서리는 둥글며, 회색 테두리·단차가 있습니다. AR.js pattern 추적이 요구하는 검은 사각형을 반지의 회색 테두리가 안정적으로 대체한다고 볼 수 없습니다.

이것이 우선 조사할 구조적 문제입니다. 단순히 작은 크기 때문이라고 단정할 수 없습니다. 이전에 검은 테두리가 있는 전체 마커 대신 로고 부분만 잘라 붙였는지 확인해야 합니다. 사진의 실제 출력물과 기존 `assets/taesung.patt`의 대응 여부도 실물 대조 없이 확정할 수 없습니다.

사진은 정지 촬영물이므로 실시간 AR 카메라의 최소 초점 거리, 흔들림, 자동노출, 처리 영상 해상도를 알려주지 않습니다. 기준 자가 없어 10mm를 사진에서 검증할 수도 없습니다. 종이 아래쪽 가장자리의 약간 불규칙한 부분과 상판 단차는 보이나, 평탄도·코팅·반사율을 계측한 것은 아닙니다. 강한 정반사가 주원인이라는 증거도 이 사진에는 충분하지 않습니다.

## 2. 30mm용 마커라서 10mm를 거부하는가?

일반 pattern `.patt`는 물리적인 mm 크기를 저장하지 않습니다. 내부 그림을 16×16으로 표본화한 B/G/R 3채널, 4방향 데이터입니다. 같은 그림을 정확히 축소했다는 이유만으로 ‘30mm 전용’ 제한에 걸리지는 않습니다. 다만 축소는 카메라에서 얻는 픽셀 수와 인쇄 선명도를 줄입니다.

`a-marker size`는 검은 정사각형 외곽 한 변의 실제 길이(m)로 맞춥니다. 이는 주로 자세·거리·가상 물체 스케일에 영향을 주며, 흐린 입력이나 없는 테두리를 복구하는 설정은 아닙니다. 이 패키지의 10mm 스티커는 흰 여백 포함이고 검은 사각형은 8mm이므로 `size=0.008`입니다. 12/15/30mm 시험에서는 각각 0.0096/0.012/0.024입니다.

근거: [AR.js marker 문서](https://ar-js-org.github.io/AR.js-Docs/marker-based/), [공식 3.4.7 패턴 인코더](https://raw.githubusercontent.com/AR-js-org/AR.js/3.4.7/three.js/examples/marker-training/threex-arpatternfile.js).

## 3. 픽셀·출력·초점·빛의 영향

같은 거리와 카메라라면 30→10mm 축소로 한 변의 영상 픽셀 수는 1/3, 면적은 1/9이 됩니다. 분석에 들어가는 영상의 해상도가 중요하며 화면 확대나 CSS 확대는 새 디테일을 만들지 못합니다.

예시 계산: 수평 시야각 70°, 정면 마커, 왜곡 무시, 검출 영상 가로 W, 검은 한 변 L=8mm, 거리 z일 때 `p ≈ W × L / (2 × z × tan(35°))`입니다. 아래는 실제 기기 측정값이나 인식 최저 기준이 아닙니다.

| 거리 | 검출 폭 640px: 검은 한 변 | 검출 폭 1280px: 검은 한 변 |
|---|---:|---:|
| 10cm | 약 37px | 약 73px |
| 15cm | 약 24px | 약 49px |
| 20cm | 약 18px | 약 37px |
| 25cm | 약 15px | 약 29px |

ratio 0.60이면 내부 그림은 위 한 변의 60%만 차지합니다. 640px·20cm 예시에서 내부는 약 11px입니다. 16×16 템플릿과 비교한다고 해서 실제 11px 입력이 더 선명해지지는 않습니다. 기울이면 한 방향 투영 길이가 대략 cos(각도) 비율로 더 줄어듭니다. 근접하면 픽셀은 늘지만 기기의 초점 한계 안으로 들어가 흐려질 수 있습니다. 기종 공통의 최소 거리나 보장 가능한 픽셀 수는 제시하지 않습니다.

| 실제 인쇄 해상도 | 10mm 전체 | 검은 사각 8mm | 내부 4.8mm (r=.60) |
|---|---:|---:|---:|
| 300dpi | 약 118도트 | 약 94도트 | 약 57도트 |
| 600dpi | 약 236도트 | 약 189도트 | 약 113도트 |
| 1200dpi | 약 472도트 | 약 378도트 | 약 227도트 |

계산은 `mm / 25.4 × dpi`입니다. 예를 들어 0.1mm 획은 300dpi에서 약 1.18도트에 불과합니다. 잉크 번짐·토너·드라이버 보간·컬러 망점 때문에 명목 dpi만으로 선명도를 보장할 수 없습니다. PDF의 벡터 도안으로 600dpi 이상 장비부터 비교하되 실제 출력물을 확대 확인하세요. PNG는 1200×1200px이며 10mm 원본 기준 3048ppi 메타데이터를 넣었지만, PNG를 열어 인쇄할 때 크기 자동 설정은 신뢰하지 말고 PDF를 쓰세요.

무광 흰 종이/스티커를 평평하게 붙이고, 투명 유광 테이프·돔 코팅·곡면 부착은 시험에서 제외한 기준 조건부터 시작합니다. 광택은 조명 각도에 따라 검은 테두리를 밝게 만들 수 있고, 그림자는 흰 여백을 어둡게 만들어 윤곽 검출을 방해할 수 있습니다. 확산된 조명에서 시작하고, 반지 턱이 검은 모서리를 가리지 않게 하세요. 흰 배경 종이를 반지 뒤에 놓아 비교하면 주변 배경 대비의 영향도 확인할 수 있습니다.

초점은 기기에서 지원하는 경우에만 제어할 수 있습니다. 본 페이지는 자동 초점 강제나 특정 렌즈 선택을 보장하지 않습니다. 디지털 줌·브라우저 페이지 확대·3D 로고 크기 조절은 광학적 개선의 대체 수단이 아닙니다. [MediaTrackConstraints 및 지원 차이](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints).

## 4. AR.js 설정과 이번 도안

공개 저장소의 `main/ar-v08.html`을 별도 내려받아 확인했습니다. A-Frame 1.6.0, AR.js 3.4.7, `patternRatio: 0.60`, `detectionMode: color_and_matrix`, 카메라 요청 1280×960이고 marker에 size 명시가 없습니다. 제공된 로컬 사본과 공개 사본은 바이트 단위로 같지는 않으므로 배포 전 최신 저장소와 대조하세요. 이 패키지는 로컬 프로젝트 장면·로고를 복사하여 독립적인 시험 페이지를 추가하는 방식입니다.

해당 페이지에 `canvasWidth/Height` 명시가 없으며, 확인한 공식 3.4.7 라이브러리의 기본 검출 캔버스는 640×480입니다. 카메라 1280 요청만으로 분석 해상도가 자동 1280이 되지 않습니다. 새 페이지는 기본 검출 1280×960과 비교용 640×480을 명시하고, 실제 카메라 트랙·검출 캔버스 값을 화면과 CSV에 표시합니다. 높은 검출 해상도는 처리 비용·발열·프레임 저하를 늘릴 수 있으므로 두 설정을 실측 비교해야 합니다.

`patternRatio = 내부 그림 한 변 / 검은 정사각형 외곽 한 변`. 흰 여백은 이 계산에 포함하지 않습니다. 검은 테두리 한쪽 폭은 `검은 한 변 × (1-ratio)/2`입니다. 도안과 런타임 ratio가 다르면 다른 영역을 비교하게 됩니다. ratio는 전체 추적 컨텍스트에 적용되므로 0.60 도안과 0.50 도안을 한 장면에 섞지 않았습니다.

| 도안 | 목적과 브랜드 보존 | ratio | 10mm 전체 중 구성 |
|---|---|---:|---|
| A-color | 제공된 태성 로고의 검정·파랑 형상 유지, 위쪽 비대칭 표식 추가 | .60 | 흰 여백 각1mm / 검은8mm / 내부4.8mm / 검은 띠 각1.6mm |
| B-mono | 같은 로고 형상을 흑백으로 통합하여 대비 비교 | .60 | A와 동일 |
| C-bold | 굵은 L과 분리된 사각 표식 중심, 원본 로고는 작게 보존 | .60 | A와 동일 |
| D-border50 | B와 같은 내부 그림, 더 두꺼운 검은 띠 비교 | .50 | 흰 여백 각1mm / 검은8mm / 내부4mm / 검은 띠 각2mm |

브랜드 가독성과 디지털 표본의 단순화는 상충합니다. A/B에서는 로고를 크게 남겼고, C에서는 작은 로고를 사람이 볼 때의 서명으로 남기면서 큰 방향 표식에 더 많은 면적을 썼습니다. D는 테두리가 두꺼워지는 대신 내부 로고가 작아집니다. 어느 방식이 실물에서 가장 나은지는 아직 결론 내리지 않았습니다. 내부 도형은 네 방향 회전에 비대칭이며 외곽 검은 사각형은 모두 연속입니다.

새 페이지는 네 도안을 하나씩 `mono` 모드로 검사합니다. A의 파랑도 밝기 대비로 사용합니다. A/B는 매우 비슷한 로고이므로 서로의 고유 식별자로 쓰는 용도가 아닙니다. B/D는 내부 그림과 `.patt`가 같고 외곽 테두리 비율만 다릅니다. 두 파일이 같은 것은 의도된 설계입니다. 로고가 아닌 기존 마커, Hiro, QR, ArUco와도 자동 호환되지 않습니다.

근거: [공식 AR.js 문서](https://ar-js-org.github.io/AR.js-Docs/marker-based/), [ARToolKit의 사각 테두리·비대칭·16×16 설명](https://github.com/artoolkitx/artoolkitx/wiki/Creating-and-using-square-pictorial-markers), [jsartoolkit marker 검출 설명](https://github.com/artoolkitx/jsartoolkit5/blob/master/doc/using_different_marker_types.html), [이번에 검사한 AR.js 3.4.7 코드](https://raw.githubusercontent.com/AR-js-org/AR.js/3.4.7/aframe/build/aframe-ar.js), [기존 공개 페이지 소스](https://github.com/Kelvin-Yoon/taesung-ar-ring/blob/main/ar-v08.html).

## 5. 파일 구성과 GitHub Pages에서 실행

- `A4-marker-tests.pdf`: A4 1페이지. 네 도안 × 10/12/15/30mm. 50mm 검증선 포함.
- `markers/*.svg`, `*.png`: 흰 여백 포함 전체 마커. SVG의 width/height는 10mm. 그림·검은 테두리를 잘라내지 마세요.
- `markers/*-inner.svg`, `*-inner.png`: 테두리 없이 내부 학습용. **이것만 출력하여 반지에 붙이면 안 됩니다.**
- `markers/*.patt`: 공식 3.4.7 인코더로 내부 그림에서 생성한 3072개 값의 4방향 BGR 패턴.
- `test.html`, `ar-test-*.html`: 선택 화면과 네 도안 전용 AR 시험 페이지. 기존 로고 상승·회전 장면 포함.
- `ar.js`, `assets/logo-geometry.json`: 제공된 프로젝트에서 복사한 장면·로고. 기존 파일을 덮어쓰지 않아도 되도록 패키지 안에 포함.
- `vendor/`: 공식 A-Frame/AR.js/인코더와 비교용 공개 페이지 사본. `assets/camera_para.dat`는 공식 기본 보정 파일이며 사용자 휴대폰을 보정한 파일이 아닙니다.
- `validation.json`: 자동 검증 기록. 실물 시험 성적표가 아닙니다.

저장소 `Kelvin-Yoon/taesung-ar-ring`에 새 폴더 `marker-lab/`를 만들고 **이 패키지 내용 전체**를 그 안에 올리면 기존 루트 페이지를 바꾸지 않고 사용할 수 있습니다. GitHub Pages 배포 후 주소는 `https://kelvin-yoon.github.io/taesung-ar-ring/marker-lab/test.html`입니다. 이는 업로드 후의 예상 주소이며 이번 작업에서 실제 업로드·배포한 것은 아닙니다. `test.html`만 따로 올리면 파일 경로가 깨집니다. HTTPS와 카메라 권한이 필요하며 스마트폰에서 로컬 `file://` 열기는 시험 방법이 아닙니다.

각 전용 페이지에서 출력물 전체 크기 10/12/15/30mm를 선택하여 적용하세요. 잘못된 크기를 선택하면 가상 물체의 거리·축척이 틀립니다. 검출 폭 1280/640을 바꾸면 페이지가 다시 열립니다. 측정 기록은 페이지 메모리에 있으므로 **도안·설정을 바꾸기 전에 CSV를 저장**하세요. 브라우저에 실제 물리 치수나 거리가 자동 측정되는 것은 아닙니다.

## 6. 재현 가능한 실물 인식 시험

1. PDF를 A4, 실제 크기 100%로 출력합니다. 페이지 맞춤·자동 축소·테두리 없는 확대를 끕니다. 50mm 선과 10mm 스티커를 자/캘리퍼스로 확인합니다. 허용 오차는 먼저 ±0.2mm 목표로 기록하되, 이는 프로젝트 관리 기준이지 엔진 공식 규격이 아닙니다.
2. 같은 프린터·같은 무광 재질·같은 휴대폰 후면 카메라로 시작합니다. 렌즈를 닦고 거치대/받침대를 사용합니다. 기종, OS, 브라우저 버전, 실제 카메라·검출 해상도, 프린터 설정을 기록합니다.
3. 각 도안 전용 페이지와 **30mm 평면 카드**로 먼저 시험합니다. 여기서 실패하면 10mm 작업을 계속하지 말고 도안/URL/카메라 권한/검은 테두리/ratio를 먼저 확인합니다.
4. 한 번에 하나의 마커만 화면에 둡니다. 15→12→10mm 평면 카드로 줄입니다. 각 조건에서 10초씩 5회 반복합니다. 매번 카드를 가려 미인식 상태를 만든 뒤 측정을 누르고, 카드를 다시 보여 최초 인식을 재시험합니다.
5. 첫 단계: 정면, 확산 조명, 거리 10/15/20/25cm, 검출 1280. 가까운 카드가 흐리면 기기의 선명한 최소 거리로 물러나고 그 거리를 기록합니다. 10cm에 억지로 고정하지 않습니다. 8cm 추가 시험은 초점이 실제 맞는 기기에서만 합니다.
6. 같은 조건을 검출 640으로 반복합니다. 안정적 상위 두 도안에 대해 기울기 0/20/40°, 회전 0/90/180/270°를 확인합니다. 기울기는 표면 법선과 카메라 시선 사이 각도로 기록합니다. 각도·거리는 자/각도기로 외부 측정합니다.
7. 평면에서 통과한 10mm 도안을 반지에 붙여 같은 조건을 반복합니다. 손을 고정한 상태와 자연스러운 손떨림을 구분합니다. 무광 평탄 부착과 원래 부착 상태, 흰 배경/주변 책상 배경을 비교합니다. 날카로운 모서리·돌출은 착용을 해치지 않게 마감하되 검은 사각형 자체를 둥글게 잘라내지 않습니다.
8. 마지막으로 실내 일반 조명·그늘·직접 조명에서 비교합니다. 광량은 조도계가 있으면 lux로 기록하고 없으면 환경 설명을 남깁니다. 불필요하게 광택 코팅을 더하는 것을 개선책으로 가정하지 않습니다.

10초 측정은 최초 인식 시간, 표시 유지율, 표시 끊김 횟수를 약100ms 간격으로 기록합니다. 브라우저 타이머·기존 추적 smoothing의 영향을 받는 **사용자 화면상의 유지율**이며 엔진 검출 프레임별 정밀 분석은 아닙니다. 잘못된 방향이나 심한 위치 떨림은 사람이 별도 기록하세요. 측정 시작 전에 이미 인식 중이었다면 최초 인식 시간이 짧게 나오는 것은 당연하므로 신규 인식 시험으로 해석하지 않습니다.

프로젝트의 예시 합격 기준(공식 보장 기준 아님): 목표 거리·각도에서 신규 인식 5회 모두 2초 이내, 각 10초 유지율 90% 이상, 엉뚱한 방향·다른 마커 오인식 없음. 이 기준을 넘긴 실제 기기·재질·조명 조합만 운영 후보로 삼으세요. 결과가 불안정하면 상판을 12~15mm로 늘리거나, 반지는 브랜드 표시용으로 두고 더 큰 별도 카드로 시작하는 방식도 비교할 수 있습니다.

## 7. 검증 범위와 남은 한계

A4 MediaBox 210×297mm를 수치 검증했고, PDF를 PNG로 렌더링하여 글자·도안·배치·검증선을 육안 확인했습니다. 출력물의 물리 오차는 프린터에서 별도로 확인해야 합니다.

`.patt`는 공식 인코더의 Canvas 16×16 표본화를 직접 사용했습니다. 각 3072개 정수, 0~255 범위, BGR 순서와 네 방향 형식을 확인했습니다. 인쇄용 SVG와 PNG와 PDF는 동일한 도형 정의에서 만들며, PDF/SVG는 벡터 원본입니다. PNG의 경계 좌표 반올림에 따른 아주 작은 차이는 있을 수 있습니다.

Edge 가상 카메라에서 네 전용 페이지의 엔진 초기화, ratio, 1280×960 검출 캔버스, 0.008m 크기, 3D 로고 로딩 및 스크립트 오류 여부를 검사했습니다. 실제 AR.js 컨트롤러에 정면 합성 마커 영상을 넣어 크기별·네 방향 인식과 빈 흰 화면 음성 대조군을 검사했습니다. 각 방향 시험 전에 빈 화면을 넣어 이전 인식의 연속 추적 영향을 줄였습니다. 자세한 값과 신뢰도는 `validation.json`을 확인하세요.

합성 영상은 노이즈·인쇄 번짐·초점 이탈·반사·곡면·손떨림·원근 왜곡을 재현하지 않습니다. 작은 픽셀 크기에서 디지털 검출에 성공해도 그 수치를 실물 인식 최소 기준으로 사용하면 안 됩니다. 1280 캔버스가 카메라 실영상의 해상도를 넘으면 단순 확대일 뿐입니다. 브라우저 기본 카메라 보정도 실제 렌즈와 다를 수 있어 거리·정합 오차가 남습니다. 실물 시험으로만 10mm 사용 가능 범위를 판단할 수 있습니다.
